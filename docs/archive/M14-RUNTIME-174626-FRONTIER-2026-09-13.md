## Performance result

Compact raw guest-array interval staging is runtime-proven active (`begin=984 end=1032 bytes=48 prefix_saved=984` first marker), but the player reports no material improvement in the heavy scenes. The old 7 MiB guest-array high-water profile no longer triggers, which means prefix-copy volume was successfully reduced and is no longer the leading explanation for the remaining lag.

Synchronous DrawDone drain remains severe. Representative samples in this run reached approximately:

- 55 ms;
- 76-91 ms;
- 165 ms;
- 185 ms maximum observed.

The late heavy scene repeatedly delivered only roughly 14-25 native retraces per wall-clock second even though the host-derived 60.75 MHz Broadway timebase continued tracking wall time.

This is a critical timing diagnosis, not merely an FPS observation: renderer work is blocking the native runtime thread long enough that scheduler-idle VI/retrace delivery falls behind while timebase-driven code continues to observe real elapsed time.

## Player-visible timing split

The player reports:

- enemies slow down with the lag;
- the flip timer slows down;
- the camera slows down and can trail behind Mario;
- Mario's horizontal movement does not slow by the same amount, making him appear to run fast relative to the camera/world.

That observation matches the log. The authoritative timebase itself is healthy; the bad behavior comes from mixing host-time/timebase-driven motion with systems advanced by delivered retrace/frame epochs. Do **not** fix this by slowing the timebase, speeding simulation, or scaling Mario. The runtime must eventually keep Wii VI/retrace semantics independent of renderer CPU stalls, or eliminate those stalls through a safe renderer separation after GPU-visible guest data becomes immutable.

## Current high-value performance work

The unsafe `ProcessingMode::Thread` experiment remains retired. Do not restore a worker that reads live mutable MEM1/MEM2.

The next runtime candidate adds a sparse diagnostic-only `M14 GX draw CPU profile` around Aurora's existing raw draw preparation. It reports one aggregate per 2048 draws and changes no FIFO/GX/frame/cache/timing semantics. Compare that CPU total against DrawDone wall time to decide whether the remaining cost is primarily per-draw decode/staging/pipeline/texture/uniform work or a non-draw boundary/synchronization cost.

PE bounding-box readback is also a measured secondary frontier. This run reached more than 2,500 GPU bbox maps. In the heavy section, submit-only readback boundaries occasionally cost about 20-26 ms while the actual map itself remained sub-millisecond. Do not bypass bbox correctness blindly; isolate whether the expensive part is render-worker submission, queue ordering, or exact GPU readback before changing semantics.

## Flip black-square regression

The black square during the 2D/3D flip remains in the safe synchronous build, so it is **not** an async-memory race.

The first logged Wii-A flip edge (`buttons=0x00000800`) is immediately followed by the runtime-proven original-GX half-scale feedback copy:

`608x480 -> 304x240, fmt=4, stride_tiles=76`.

Keep the half-scale semantic: it is source-backed GX behavior. The remaining bug is now a narrow flip-feedback/effect frontier. Investigate the exact flip draw/copy/material state rather than reopening generic texture debugging. GX_LO_OR remains fidelity debt because OpenSPM currently approximates bitwise OR with component-wise Max, but it is not yet proven to be the black-square cause.
